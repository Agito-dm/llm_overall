# День 2 — Сравнение промптов

## Цель

Цель этапа — оценить влияние формулировки промпта на корректность структуры и качество ответов LLM. Для сравнения использовалась модель `gemini-3.5-flash-lite` и три одинаковых входных текста: вопрос о механизме attention, сообщение об ошибке с библиотекой pandas и отзыв покупателя о ноутбуке.

## Варианты промптов

- **A — Basic.** Краткая инструкция с запросом summary, трёх ключевых мыслей и полезного ответа в формате JSON.
- **B — Constrained.** Подробная инструкция с названиями полей, ограничениями длины и требованием возвращать только JSON.
- **C — Few-shot.** Инструкция с аналогичными ограничениями и примером входного текста с ожидаемым ответом.

## Результаты

Эксперимент проводился дважды на одинаковых трёх текстах для каждого варианта.

| Вариант | Успешные ответы за запуск | Проверки формата за запуск | Первый запуск, среднее время | Второй запуск, среднее время |
|---|---:|---:|---:|---:|
| A | 0/3 | 0/9 | — | — |
| B | 3/3 | 9/9 | 6,87 с | 1,19 с |
| C | 3/3 | 9/9 | 8,18 с | 2,26 с |

Успешным считался ответ, который удалось преобразовать в JSON и который прошёл базовую проверку структуры пайплайна. Отдельные проверки формата оценивали длину summary, наличие трёх непустых ключевых мыслей и краткость итогового ответа. Эти показатели не отражают фактическую точность и полезность содержания.

## Анализ результатов

**Вариант A** завершился ошибкой `ValueError` во всех трёх случаях в обоих запусках. В результатах эксперимента сохранён только тип исключения, поэтому установить конкретную причину отказа по текущим логам невозможно.

**Варианты B и C** успешно прошли все проверки формата. В ответах были выделены основные мысли исходных сообщений и сохранена их тематика. В обоих запусках вариант B показал меньшее среднее время обработки, чем C.

При ручном просмотре обнаружены ограничения качества. Вариант B в ответе на жалобу покупателя слишком уверенно упоминал возможность требовать компенсацию без уточнения условий. Вариант C сообщал о передаче отзыва в службу контроля качества, хотя выполнение такого действия в приложении не предусмотрено. Таким образом, корректный JSON сам по себе не гарантирует достоверный или уместный ответ.

Во втором запуске среднее время ответа сократилось с 6,87 до 1,19 с для B и с 8,18 до 2,26 с для C. При этом результаты проверок формата не изменились. Причина ускорения не установлена; возможное объяснение — изменчивость задержек API и сетевых условий. Размер выборки недостаточен для надёжного сравнения производительности.

## Выбранный вариант

**Вариант B — Constrained** выбран основным для дальнейшего развития пайплайна. Он успешно прошёл формальные проверки на всех тестовых текстах, обеспечил достаточно содержательные ответы и не потребовал дополнительного примера в промпте. Варианты A и C сохранены для последующих сравнений.

## Ограничения и дальнейшее развитие

Сравнение основано на двух запусках трёх тестовых текстов для каждого промпта. Автоматическая оценка проверяла формат, тогда как содержательные недостатки выявлялись при ручном просмотре. Для более уверенных выводов о стабильности и скорости необходимы дополнительные повторения и расширение набора примеров.

На следующих этапах предусмотрены проверка расширенной JSON-схемы с помощью Pydantic, подробная диагностика ошибок, обработка неудачных запросов и повторное тестирование на более разнообразных входных данных.
