# Day 6 – Reliability, Guardrails & Fallback

## Цель

Повысить устойчивость LLM-пайплайна к временным ошибкам API, некорректным ответам модели и нарушениям формата без изменения архитектуры предыдущих дней.

## 1. Retry при ошибках API

В `clients/llm_client.py` реализованы повторные попытки запросов.

Параметры:

- Максимум 3 попытки, включая первоначальную.
- Задержки 1 и 2 секунды (exponential backoff).
- Повтор при сетевых ошибках, тайм-аутах, HTTP 408, 409, 429 и 5xx.
- Ошибки авторизации и некорректных запросов не повторяются.
- После исчерпания попыток исходное исключение передаётся вызывающему коду.

Автоматические повторы OpenAI SDK отключены, чтобы избежать дублирования retry.

## 2. Fallback generation

В `core/multi_step_pipeline.py` добавлена функция `generate_final_answer()`.

Если основной ответ не проходит валидацию, выполняется дополнительная генерация с более строгим промптом.

Fallback используется при:

- Некорректном JSON.
- Отсутствии обязательного поля `final_answer`.
- Пустом ответе.
- Превышении разрешённой длины.

Повторяются только действия этапа генерации. Извлечение смысла, классификация и формирование промежуточных данных выполняются один раз.

Если повторный ответ также невалиден, выполнение завершается с `ValueError`.

## 3. Guardrails

Выполняется проверка итогового ответа средствами Pydantic и Python.

Установлены ограничения:

- Не более 80 слов в `final_answer`.
- Не более 2000 символов в `final_answer`.
- Не более 12000 символов в исходном ответе генерации.

Для корректного ответа сохраняется обычная структура результата.

При ошибке валидации self-check итоговый ответ сохраняется, но проверка качества помечается как неуспешная (`is_valid=False`, `error`).

Ошибки API не маскируются механизмом fallback.

## 4. Логирование

Добавлено логирование:

- Номера попытки и используемой модели.
- Времени выполнения запросов.
- Типа ошибки и возможности повторной попытки.
- Запуска и результата fallback.
- Проблем валидации и self-check.

API-ключи и содержимое пользовательских запросов специально не записываются в новые диагностические сообщения.

## 5. Негативные тесты

Проверены следующие сценарии:

| Сценарий | Ожидаемое поведение |
|---|---|
| Сетевая ошибка | Повтор запроса |
| HTTP 503 | Повтор запроса |
| Три последовательные ошибки | Исключение после третьей попытки |
| HTTP 400 | Немедленное исключение |
| Пустой ответ | Ошибка либо fallback |
| Невалидный JSON | Fallback |
| Ответ более 80 слов | Fallback |
| Слишком длинный исходный ответ | Fallback |
| Повторно невалидный ответ | Исключение |
| Некорректный self-check | Результат помечается как непроверенный |
| Ошибка API при генерации | Не запускает fallback |
| Ошибка API при self-check | Передаётся вызывающему коду |

Испытания выполнены с имитацией ответов и ошибок API без расходования квоты Gemini.

## 7. Ограничения

- Retry не устраняет длительную недоступность провайдера или исчерпанную квоту.
- Fallback исправляет формат ответа, но не гарантирует достоверность содержания.
- Ограничения длины применяются к итоговой генерации, а не ко всем промежуточным ответам.
- Self-check не является независимой проверкой фактов.
- Проект остаётся учебным mini-product без сложных механизмов мониторинга и восстановления состояния.
